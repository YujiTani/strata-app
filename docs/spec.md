# 機能仕様（洞窟発掘 × 放置ゲーム）

> 「何を作るか（機能の範囲と MVP の線引き）」を定義する。
> ゲーム挙動の詳細は `game-design.md`、整合性方針は `architecture.md`、テーブルは `data-model.md`。

---

## このゲームは何か（1行）

ランダム生成された洞窟を発掘して素材を集め、村を発展させる。村の発展に必要な素材は人により異なるため、
**自給自足できない素材を売買する市場**が生まれる。その市場こそが、主軸「データ整合性を守る堅牢な
バックエンド」を学ぶための題材。

---

## アカウント登録（MVP・最初に必要）

- ゲーム開始時に **町の名前** と **プレイヤー名** を入力してアカウント登録。
- 認証方式は未定（匿名デバイスID + トークンで足りるか要検討 → オープン論点）。

---

## コアのゲームループ

```
 (1) 発掘（ランダムmap）→ (2) 素材・レア獲得 → (3) 村を発展（素材＋通貨を消費）
                                                │
                       (4) 足りない素材を市場で売買 ←┘（他プレイヤーと取引＝経済）
```

詳細な採掘の挙動・スタミナ・パラメータは `game-design.md` を参照。

---

## 設計の最重要方針: データ駆動にする

量（素材種・村レシピ・フィールド等）は学習目的ではなく、システム完成後に AI で拡張する前提。
その拡張が「行を足すだけ」で済むよう、**仕様をコードにハードコードせずテーブルのデータとして持つ**。

| データ駆動にするもの | 持ち方 |
|---|---|
| ドロップ内容・確率 | `drop_tables` |
| 村のアップグレード要件 | `building_recipes`（追加予定） |
| アイテム定義 | `item_defs` |

> 注意: これが崩れると「後から AI で拡張」という前提自体が崩れる。最初の設計で必ず守る。

## MVP の線引き

### MVP に入れる（コア）
- アカウント登録（町名・プレイヤー名）
- 発掘とドロップ（サーバー確定。詳細は architecture.md / game-design.md）
- 通貨ウォレット（残高は `ledger_entries` から導出・複式元帳）
- マーケット出品・購入（**山場。FOR UPDATE の主役**）
- デイリー報酬（`UNIQUE(player_id, claim_date)` で冪等）
- 村アップグレード（素材＋通貨を 1 トランザクションで消費・全成功 or 全失敗）
- スタミナ / 耐久 / ツルハシパワー / レベル経験値 / インベントリ上限（game-design.md 参照）
- 建物 2 種（ツルハシ生産・スタミナ拡張）

### MVP に入れない（non-goal）
- 採掘の深度・フィールドのランダム性・天候・特産品（データ駆動で後から）
- モンスター戦闘（non-goal 固定）
- 資産家ランキング（設計は考えるが MVP 実装外）
- リアルタイム通知、フレンド、ギルド
- 認証の本格対応、レート制限（デモで「線を引いた」と語る対象）
- 常駐アプリ化（Tauri）、Steam 掲載

## オープンな論点（今後詰める）
- `building_recipes` の具体スキーマ（data-model.md に反映予定）
- 市場の手数料率（通貨シンク）と各種付与レート（経済バランス）
- 認証方式
- API エンドポイント一覧とエラー形式の規約
- 資産家ランキングの集計の持ち方（リアルタイム集計 vs 定期バッチ）

> ドロップ抽選方式は決定論的抽選（SEED ベース）に確定 → `architecture.md` 参照。
