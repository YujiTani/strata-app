# ADR-0005: データベースとリージョン

- ステータス: 決定
- 日付: 2026-07-16

## コンテキスト

Postgres（`FOR UPDATE`等の行ロックが使える本格的なRDB）が必要。個人開発でセルフホストの運用負荷は
避けたい。アプリ本体をどこに置くか（`docs/adr/0010`）ともレイテンシの観点で連動する。

## 決定

Neon（マネージドPostgres）を採用する。リージョンは東京が無いため、シンガポール（ap-southeast-1）を選択。

## 検討した選択肢

| 選択肢 | 採用しなかった理由 |
|---|---|
| セルフホストPostgres（VPS等） | 運用（バックアップ・パッチ適用等）が主軸の学習と無関係な作業を増やす |
| Supabase | TODO: 比較検討の詳細を自分の言葉で補足する |

## 理由

マネージドで運用負荷が低く、無料枠で学習用途に十分。東京リージョンが無いため、
アプリ（Fly.io）もDBに合わせてシンガポールに配置し、往復レイテンシを抑える方針にした（ADR-0010参照）。

## 結果・トレードオフ

- 得たもの: 運用負荷ゼロでのPostgres利用
- 払ったコスト: 東京リージョンが無いことによる物理的なレイテンシ（Week5で実測比較予定、`docs/roadmap.md`）
- 現在保留中の課題: 開発用と本番用で同一のNeon DBを共用している（`docs/progress.md` 2026-07-24 / 07-27）。
  分離はNeonのbranch機能で低コストに行えるが、Week3時点では意図的に後回しにしている
