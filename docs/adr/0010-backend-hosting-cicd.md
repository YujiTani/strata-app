# ADR-0010: バックエンドのアプリ基盤・ビルド・CI/CD

- ステータス: 決定
- 日付: 2026-07-13

## コンテキスト

Week1の目標は「本番URLで動く骨格をpushだけで自動デプロイできる状態にする」こと
（ウォーキングスケルトン、`docs/roadmap.md`）。DB（Neon）はシンガポールにある。

## 決定

アプリ基盤は Fly.io（シンガポール）。ビルドは自作Dockerfile、デプロイはGitHub Actionsで
push時に自動実行する。

## 検討した選択肢

| 選択肢 | 採用しなかった理由 |
|---|---|
| Cloudflare Workers | インタラクティブなトランザクション保持がHyperdrive推奨の使い方と衝突する
（`FOR UPDATE`のためのTCPセッション保持が主軸の要件、ADR-0006）。加えてDocker化の学習機会が消える |
| お任せデプロイ（Buildpack等、Heroku系のPaaS） | ビルドの中身がブラックボックス化し、
「モノレポからのcontext切り出し」等の学習機会が失われる。今回は学習目的のためあえて自作する |

## 理由

DBがシンガポールにあるため、アプリ⇔DB間の往復レイテンシを抑えるにはアプリも同リージョンに置くのが有利。
Dockerfileを自作することで、モノレポからのビルドcontext切り出し・マルチステージビルド等を実地で学べる。

## 結果・トレードオフ

- 得たもの: push一発で本番反映される骨格（Week1で達成）
- 払ったコスト: Dockerfile自作・GitHub Actions設定の分だけ、お任せデプロイより初期セットアップに時間がかかった
- 運用上の実例: `fly.toml`にヘルスチェックが未設定のため、クラッシュループ中のマシンに対する
  ローリングデプロイが実機に反映されないまま「成功」表示になる問題に遭遇した
  （`docs/progress.md` 2026-07-24、学習ノート `2026-07-24-crashloop-deploy-gap`）。
  ヘルスチェック追加は未対応のまま残っている
