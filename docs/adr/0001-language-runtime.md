# ADR-0001: 言語・ランタイム・パッケージマネージャ

- ステータス: 決定
- 日付: 2026-07-13（2026-07-27 検収・改訂）

## コンテキスト

8週間・約120時間の個人開発。学習の主軸は「データ整合性を守るバックエンド設計」であり、
二重販売や残高の二重計上を防ぐロジックを自分の手で実装して体験的に学ぶことが目的。
言語・ランタイムの選定そのものに時間を使いすぎず、主軸に時間を回したい。

## 決定

言語は TypeScript、ランタイム/パッケージマネージャは Bun を採用する。
バックエンド・クライアント（`apps/client`）共通で使う。

ただし**ランタイムを単独で選んだのではなく、Webフレームワーク（Elysia.js / ADR-0003）とセットで決まった**。

## 検討した選択肢

| 選択肢 | 採用しなかった理由 |
|---|---|
| Node.js + npm | TSの直接実行に tsx かビルドステップ、環境変数に dotenv と、周辺ツールを個別に組み合わせる必要がある |
| Node.js + pnpm | install速度・ディスク効率は優秀で、**エコシステムの成熟度ではこちらが上**。ただし pnpm はパッケージマネージャ単体であり、TS実行・env読み込みは別途必要。加えて Elysia.js（ADR-0003）が Bun ネイティブ前提のため、この構成では選べなかった |
| Deno | Elysia等の候補フレームワークとの親和性が薄い |

## 理由

### 起点は型安全（フレームワークとの連動）

フロント・バックを同じ言語で書く以上、両者で型を共有したかった。当初は tRPC の利用を想定していたが、
Elysia.js は Eden Treaty により**標準機能で** end-to-end 型安全が得られ、記述コストを大きく下げられる。
Elysia.js は Bun ネイティブ前提のため、ランタイムも Bun になった。詳細な比較は ADR-0003 を参照。

### TypeScript

自分が最も速く書ける言語であること。フロント・バックを1言語で書けるため文脈の切り替えコストも下がる。
8週間という制約下では、**個人の記述速度は正当な選定基準**と判断した。

### Bunの「速さ」は3つに分解して評価した

| 何の速さ | 今回効いたか | 判断 |
|---|---|---|
| `bun install` が速い | 効いた | CI・Dockerビルドで毎回走るため、待ち時間に直結する |
| ツール統合（TS直接実行・`.env`自動ロード・バンドラ同梱） | 効いた | 周辺ツールの選定・接続に時間を使わずに済む。**pnpm との実質的な差はここ** |
| 実行時が速い | **選定基準に入れていない** | ↓ |

実行時性能を基準から外したのは、このアプリが **I/Oバウンド**だから。
1リクエストの処理時間は、日本↔シンガポール間のネットワーク往復と、Neonへの複数回のDB往復
（`FOR UPDATE` / `UPDATE` / `COMMIT`）が支配している。サーバー内の計算はサブミリ秒のオーダーで、
ランタイムを速くしても全体の応答時間は縮まない。

→ 「TypeScriptは実行速度に優れた言語ではない」という事実は、**今回のワークロードでは不利にならない**。
CPUバウンドな処理が主になれば、この前提は崩れる。

## 結果・トレードオフ

**得たもの**: 環境構築に使う時間の圧縮。install / CI の高速化。

**払ったコスト**: Bunのエコシステムの若さ。実際に3件踏んだが、性質は分けて認識している。

| 事象 | 分類 | 内容 |
|---|---|---|
| Vitest が Bun 上でも Node 実行になる | **Bun起因** | Vitest側がBunを第一級サポートしていない。エコシステムの若さの帰結であり、**選定時に払うと分かっていたコスト**（ADR-0008） |
| Docker上で `.env` が読めない（Issue #4） | **自分起因** | Bunの`.env`自動ロードは CWD基準という**仕様どおりに動作していた**。原因は Dockerfile の `WORKDIR` のズレと、`dotenv.config()` を残して二重にしていたこと |
| `bun.lock` と `--frozen-lockfile` の構成不一致 | **半々** | `npm ci` でも同種の構成不一致は起きる。ただし `bun.lock` がワークスペース全体を単一ファイルに記録する挙動は関係している（ADR-0002） |

3件とも解決済みで、現時点では許容範囲内と判断している。

**ロックイン**: ランタイムとフレームワークをセットで選んだため、**Bunをやめる＝Elysia.jsもやめる**ことになる。
切り戻しのコストは小さくない。

**覆すきっかけ**: Bun固有のバグに繰り返し当たり、切り分けコストが主軸の学習時間を侵食し始めたとき。
その場合は Node + pnpm 構成（フレームワークの再選定を伴う）への移行を検討する。
