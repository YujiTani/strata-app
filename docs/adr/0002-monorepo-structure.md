# ADR-0002: モノレポ構成（Bun workspaces）

- ステータス: 決定
- 日付: 2026-07-13（2026-07-27 検収・改訂）

## コンテキスト

サーバー（バックエンド）・クライアント（Phaser）・両者で共有したいコードが存在する。
別リポジトリに分けるか、1つにまとめるかを決める必要があった。

このゲームはクライアント側で採掘の演出がリアルタイムに走り、プレイヤーは掘りながら
「何が出そうか」を画面で見る（予測表示 / `architecture.md`）。この体験を残す限り、
クライアントとサーバーは**独立に同じ答えへ到達する必要がある**。

> 予測表示をやめ、サーバーが確定した結果を返してから演出する設計なら、共有すべきコードは消え、
> モノレポの主な根拠も消えていた。採らなかったのは、採掘が「ボタンを押して結果を待つ」だけになり、
> リアルタイムに掘る体験が成立しなくなるため。**UXのために整合性設計の複雑度を引き受けた**判断である。

## 決定

Bun workspaces を使ったモノレポ構成にする。`apps/server` `apps/client` `packages/shared` の3ワークスペース。

`packages/shared` には、**フロントとバックが同じ答えを出すために必要な共通処理**だけを置く。
型データや共通モジュールがここに入る。
**メインのデータを確定させる処理はバックが持つ**（`apps/server` の外に出さない）。

### 依存グラフはワークスペース数と一致しない

```
apps/client  → packages/shared
apps/client  → apps/server      （型のみ / Eden Treaty）
apps/server  → packages/shared
```

クライアントがサーバーの型を直接 import するのは Eden Treaty（ADR-0003）の帰結。
これは**利点であると同時に結合**でもある。型が常に最新に追随する一方、
サーバーのルート定義を変えるとクライアントの型が壊れる。

## 検討した選択肢

| 選択肢 | 採用しなかった理由 |
|---|---|
| サーバー/クライアント別リポジトリ（コードをコピー） | SEED から map・ドロップを再現する決定論的ロジックを**同一コード**として持てない。コピーを2つ置けば、いつか片方だけ直る |
| 別リポジトリ + private npm package として publish | 同一コードにはできるが、変更のたびに version 更新 → publish → 依存側で更新が要り、**バージョンごとの差が出るので管理が面倒**。片方だけ古い版を見る状態（バージョンスキュー）が起きれば、避けたかったズレがそのまま復活する。加えて Eden Treaty の型は publish できるビルド成果物ではないため、型を配る仕組みを別途組む必要がある |
| npm / pnpm workspaces | **ワークスペース機能としての差はほぼ無い。無いからこそ、パッケージマネージャを2つ持ち込まない方を取った**（ランタイムは Bun / ADR-0001） |

3行目の Eden Treaty が決定打で、**Elysia.js を選んだ時点でモノレポはほぼ必然だった**。
ADR-0001 の「Elysia を選んだから Bun」と同じ連鎖の続きにあたる。

## `packages/shared` の線引き

判定基準はひとつ。**クライアントとサーバーが独立に同じ答えへ到達する必要があるか。**

| `packages/shared` に置く | `apps/server` だけが持つ |
|---|---|
| SEED から乱数列を作る決定論 PRNG | 残高の更新・通貨の増減 |
| map（地形）の生成規則 | 所有権の移動（出品・購入） |
| ドロップ抽選のテーブル・確率 | 行ロック `FOR UPDATE` |
| 両アプリが使う型・定数・検証スキーマ | 冪等キーの処理・複式元帳への記帳 |

shared に置いたコードは**クライアントに配信され、誰でも読める**。出現率も地形の生成規則も読まれる。
それでも成立するのは、守っているのが秘匿ではなく**確定させる権限の非対称**だからである。

- クライアントが精算時に送るのは「**どこまで進むことができたか**」という進捗の数値だけで、
  ドロップの中身は送らない。
- サーバーは同じ SEED から自分で計算して確定する。**クライアントの計算結果を受け取らないので、
  照合という工程がそもそも存在しない。**
- 送られてきた進捗は、経過時間・スタミナ・ツルハシ性能から算出した上限と突き合わせ、
  **超過していれば拒否する**（丸めない / `architecture.md`）。

> ドロップ内容を送らせないのは、SEED と進捗があればサーバーが自力で計算できるからである。
> **受け取っても情報が増えないのに、偽装できる口だけが増える。**

なお、共通の依存パッケージ（zod 等）は `packages/shared` の役割ではない。
各ワークスペースの `package.json` に書けば済む。ここは自分たちが書いたコードの置き場である。

## 理由 — 共有しないと何が壊れるか

同じ決定論 PRNG を共有せず、クライアントとサーバーで別々に実装すると、
**SEED 復元時のデータがずれる**。乱数生成の定数がひとつ違うだけで、以降の抽選結果は全部変わる。

このとき重要なのは、**サーバーはそのズレを検知できない**という点である。
サーバーはクライアントの計算結果を受け取っていないので、比較する相手がいない。
自分の計算結果を平然と確定させる。

```
クライアントの画面      : 「レアが出た！」  ← 幻
サーバーが確定した結果  : 石
プレイヤーの手元に入る  : 石
```

壊れるのはデータ整合性ではなく**プレイヤーの信頼**である。そしてサーバー側からは何も見えない。
検知できない以上、**そもそもズレない構造にするしかない**。
「一致を確認する」のではなく「確認しなくても一致している」を担保する、という設計判断。

## 結果・トレードオフ

### 得たもの

- 共有コードの単一ソース化。参照先が1つしかないため、上記のズレが構造的に起きない
- Eden Treaty による end-to-end 型安全が、追加の仕組みなしで成立する

### 払ったコスト（実際に踏んだもの）

| 事象 | 内容 |
|---|---|
| `bun.lock` × `--frozen-lockfile` の構成不一致 | `apps/client` 追加時に `bun.lock` がワークスペース全体を記録するようになり、server 用 Dockerfile のビルドが落ちる構成になった。client の `package.json` をビルドコンテキストに置いて解決（ADR-0001 の分類では「**半々**」） |
| ビルドコンテキストがルートに固定される | `apps/server` 単体を切り出せないため、Dockerfile の context をリポジトリルートに置く必要が生じ、`.dockerignore` の設計が要るようになった |
| 1リポジトリから2箇所へデプロイ | `apps/client` だけの変更でも `BE_deploy` が走り、本番サーバーが再デプロイされていた。`paths-ignore` で `docs/**` と `**/*.md` を除外して対処 |

**`paths` ではなく `paths-ignore` を選んだ理由**: 両者は列挙を漏らしたときに倒れる向きが逆である。
`paths` は書いたものだけ走るため、`fly.toml` や `.dockerignore` の列挙を1つ忘れると
**直したのに本番へ反映されない**（CI は緑のまま実機だけ古い）。
`paths-ignore` は書いたものだけ走らないため、漏れても**余計にデプロイが走るだけ**で済む。
デプロイのように「反映されない」が致命的な対象には、安全側へ倒れる方を選ぶ。

### 解決していない弱点

モノレポにしても消えていない問題がある。取り繕わずに記録しておく。

| 弱点 | 内容 |
|---|---|
| **バージョンスキューは消えていない** | クライアントは**ビルド済みバンドルとして配信される**。サーバーだけ先にデプロイされ、古いバンドルを掴んだままのタブが残っている間、両者の抽選結果は一致しない。publish 方式で懸念したスキューは、**publish 時点からデプロイ時点へ移動しただけ**である。対策は未定（SEED 発行時にロジックのバージョンを載せて突き合わせる等） |
| **実行環境差** | サーバーは Bun（JavaScriptCore）、クライアントはブラウザ（V8 等）で動く。ソースが同一でも、一致が保証されない演算がありうる。整数演算（`Math.imul`・ビット演算）に閉じる方針にすべきだが、それを強制する仕組みは置いていない |
| **ズレの検知手段が無い** | 上記のとおりサーバーは検知できない。設計上の割り切りとして受け入れたが、運用側の受け皿（アラート・突き合わせバッチ等）は未整備 |
| **テストが書けていない** | 同一プロセスで同じモジュールを import して結果を比較するテストは、**この故障モードを1つも捕まえない**（同じ実装を2回呼んでいるだけのため）。必要なのは別ランタイムで同じ SEED を走らせて出力を突き合わせるテストだが、未着手 |
| **CI の一貫性が崩れている** | `FE_ci.yml` の `paths` に `apps/server/**` が含まれていない。依存グラフ上クライアントはサーバーの型に依存しているため、サーバーのルート定義を変えてクライアントの型が壊れても FE の CI が走らない。要修正 |
| **決定の根拠を前借りしている** | 現時点の `packages/shared` の中身は定数と汎用 `clamp` のみで、**決定論 PRNG はまだ存在しない**。このADRの主根拠は「これから置くもの」に依拠している |

### 覆すきっかけ

- `packages/shared` が最後まで「型と定数」だけに落ち着き、決定論ロジックが入らなかったとき。
  その場合モノレポの根拠は Eden Treaty 単独になるため、理由を書き直す
- クライアントを別チーム・外部に渡す必要が生じたとき。
  `apps/client` は `apps/server` の型に直接依存しているため、切り出しには型の配布方法の再設計を伴う
