# ADR-0004: ORM・マイグレーション

- ステータス: 決定
- 日付: 2026-07-16

## コンテキスト

主軸は「データ整合性を守る堅牢なバックエンド設計」であり、行ロック（`SELECT ... FOR UPDATE`）を
クエリレベルで明示的に書けることが必須要件。ORMがそれを隠蔽・抽象化しすぎると学習にならない。

## 決定

Drizzle + Drizzle Kit を採用する。

## 検討した選択肢

| 選択肢 | 採用しなかった理由 |
|---|---|
| Prisma | 生成されるクライアントAPIが高レベル抽象すぎて、`FOR UPDATE`のような行ロックをクエリビルダで
明示するのが難しい（Prismaの`$queryRaw`に頼る必要が出て、型安全性の恩恵が薄れる） |

## 理由

Drizzleはクエリビルダ（`db.select()...`）で`.for('update')`を明示的にチェーンでき、
「今どの行をロックしているか」がコード上で読める。これは主軸（行ロックで二重販売を防ぐ、Week3の山場）と直結する。

## 結果・トレードオフ

- 得たもの: 行ロックの明示性。ただし**リレーショナルクエリAPI（`db.query.*`）には`.for()`が無い**という制約があり、
  ロックが必要なクエリは常にクエリビルダ（`db.select()`）側で書く必要がある（`docs/data-model.md`参照）
- 払ったコスト: `sql`タグに埋めたJS定数がプレースホルダ（`$1`）に化ける、という落とし穴に遭遇し、
  `sql.raw()`の使い分けを学ぶ必要があった（学習ノート `2026-07-17-drizzle-sql-raw-ddl`）
