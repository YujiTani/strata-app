# アーキテクチャ方針（洞窟発掘 × 放置ゲーム）

> 「どう設計するか（整合性・権威・検証の方針）」を定義する。主軸に最も直結するドキュメント。
> 関連: 機能は `spec.md`、ゲーム挙動は `game-design.md`、テーブルは `data-model.md`。

---

## 第一原則: すべてサーバーが正

ドロップ・採掘結果・通貨・所有権は**サーバーが確定する**。クライアントは「意図」を送り、描画と演出に徹する。
クライアントが「結果」を決めて送る設計は不正の温床になるため**採らない**。

---

## 採掘のリアルタイム性とサーバー権威の両立

このゲームはクライアントで採掘シミュレーション（衝突→ブロック耐久減少→破壊→ドロップ）が
リアルタイムに走る。だが結果の確定はサーバーが握る。両立のための方針:

### 採用: 案A（クライアント＝演出、サーバー＝確定）
- クライアント: SEEDから map を再現し、ツルハシを振る/ブロックが壊れる**演出**を行う
- サーバー: 結果（何がドロップしたか、通貨・在庫の変化）を**確定**する

### 精算の頻度: まとめて精算（確定）
- 1打ごと・1ブロックごとにAPIを叩かない（負荷が非現実的）
- 「一定間隔」または「街への帰還時」に、クライアントが**意図**（例: SEED=X の map を N 秒ぶん発掘した）を送る
- サーバーがまとめて結果を確定する
- → 放置報酬の冪等な精算と同じ構造。学んだパターンを再利用できる

### サーバーの検証境界（🔒 主軸そのもの・自分で設計する）
- map とブロック配置は SEED から決定論的に生成 → サーバーも同じ map を再現できる
- 横スクロール一方向なので、進捗は「進んだブロック数」1 つで表せる
- 「N 秒・開始時のスタミナ・ツルハシ耐久・ツルハシパワーから、**最大何ブロック進めるか**」の上限をサーバーが計算できる
- クライアントの報告がその上限を超えたら**弾く**（＝進捗水増し攻撃を防ぐ）
- 上限超過は黙って丸めるのではなく**明確に拒否する**方針（デモの「攻撃を弾く」実演に直結）
- 完全なリプレイ検証まではやらない（8 週間ではオーバースペック・主軸から外れる）

## ゲーム形式の前提（検証を単純にする土台）

- 採掘は **2D 横スクロール・一方向（右→左）に進むだけ**。経路の自由度はない。
- そのため「どこまで掘れたか」は **1 つの距離（進んだブロック数）** で表せる。
- クライアントが精算時に送るのは **進捗（ブロック数）だけ**。ドロップ内容そのものは送らない。

## ドロップ抽選方式（確定: 決定論的抽選）

横スクロール一方向ゆえ決定論的再現が現実的な難易度に収まるため、**決定論的抽選を採用**する。

### SEED を送る（結果一覧は送らない）
- 発掘開始時、**サーバーが SEED（種）を発行**する。
- クライアントはその SEED から map とドロップを**自分で再現**して予測表示する。
- サーバーは精算時、**同じ SEED から自分で再計算**して結果を確定する。
- → クライアントとサーバーが**独立に同じ答え**にたどり着く。サーバーはクライアントを信用しない。

```
OK : サーバーは SEED だけ送る → 両者が独立に同じ結果を再計算
NG : サーバーが「1番目=鉄, 3番目=レア…」と結果一覧を送る
     → クライアントが中身を盗み見て攻略・改ざんできる。権威が漏れる
```

### 決定論 PRNG を packages/shared に置く（🔒 設計は自分・演出実装は AI 可）
- `Math.random()` は SEED 指定不可なので**使わない**。SEED から決定論的に乱数列を生む
  seedable PRNG を実装し、**`packages/shared` に置いてクライアント/サーバーで同一コードを使う**。
- 別々に実装すると僅差で結果がズレ、予測が外れる。共有が必須。
- 🔒 **設計判断（決定論にする・shared に置く・どの入力から抽選するか）は本人が握る**（権威と検証の土台）。
  ✅ それをクライアント画面で見せる演出実装は AI に委譲可。

## AI エージェント活用の線引き（難易度ではなく「主軸との距離」で引く）

```
✅ AI に任せてよい（学ぶスコープ外）
   - クライアントの map 描画・衝突アニメ・ツルハシの演出
   - SEED からクライアント側で map を再現する処理
   - クライアントの「予測表示」ロジック
   - ゲーム内容の量的拡張（素材種・レシピ・フィールド等のデータ追加）

🔒 自分で握る（主軸そのもの。AI に丸投げすると市場価値が消える）
   - サーバーが報告を検証するロジック（上限計算・水増し弾き）
   - ドロップ確定・通貨・所有権移動をトランザクションで処理する部分
   - 行ロック（FOR UPDATE）・冪等性・複式元帳の設計
   - SEED をサーバーでどう扱うかの設計判断（決定論にするか否か）
```

> この線引き自体が「スコープを選んだ判断」として面接の語り材料になる。
> 「演出はAI、整合性は自分」を明示的に説明できることが価値。

## DB接続・実装の注意（再掲・data-model.md と重複可）
- 接続は**素のTCP標準ドライバ（`postgres`）**。`@neondatabase/serverless`（HTTP）は
  インタラクティブtrを保持できず `FOR UPDATE` が成立しないため使わない。
- マイグレーションは直結（unpooled）、アプリ実行はプール接続。
- 行ロックは Drizzle の `.for('update')` をクエリビルダで明示。
